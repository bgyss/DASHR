# Benchmark and correctness protocol

## Purpose and current evidence

This protocol makes optimization and port claims reviewable. No dataset or timing run exists yet. Thresholds below are proposed acceptance criteria, not measured results or established universal tolerances. Freeze the chosen thresholds before the first comparison, and retain raw artifacts when revising them.

There are three references with different jobs: the original D3D11 output for translation parity, a double-precision CPU math/trace oracle for small cases, and a high-resolution displaced mesh or converged trace for surface quality. Matching a bug in the demo establishes parity, not geometric correctness. Blender displaced-mesh comparison is valid only after matching displacement scale, normals, interpolation, camera, color handling and pose.

## Fixture set

| Fixture | Question | Required observations |
| --- | --- | --- |
| Flat chart, constant height | Are coordinates, depth and basis conventions correct? | Analytic hit point, UV and normal |
| Flat chart, ramp and thin spikes | Does traversal skip detail? | Hit mask, hit distance, grazing-angle behavior |
| Procedural tube, paused | Is initial translation faithful? | Primary and shadow outputs plus all atlas planes |
| Tube, bending sequence | Does distortion damping remain stable? | Frame series, step distribution, invalid bases |
| Inflated cube across seams | Does chart transport preserve position? | Teleport destinations, seam sign, seam image crops |
| Pinched tube/cube | Is known failure diagnosed? | Tornado/repeated-teleport counts, budget status; no expectation of universal success |
| Imported smooth closed mesh | Does authoring generalize? | Unique UV coverage, seam validation, rig parity |
| Overlap, mirrored UV, open/hard/nonmanifold edges | Are unsupported inputs rejected? | Specific importer diagnostics, no silent remapping |
| Two intersecting/occluding assets | Is scene depth correct? | Hit depth versus shell depth, silhouette/occlusion disagreement |
| Scaled/skewed basis, large coordinates | Is compressed storage safe? | Basis conditioning, map and hit error |

Add CPU tests for affine basis inversion, points versus directions, mode-1 anchor/gutter correction, skin weights, edge orientation and uniform offsets. Include near-zero determinants, NaNs and invalid image sizes. CPU tests alone cannot verify GPU interpolation, raster conventions or image parity.

## Fixed capture manifest

Each run records commit, dependency lock hash, fixture hash, shader variant, backend, adapter identity, OS/toolchain/driver, enabled features/limits, render size, atlas size, image formats, camera/projection, pose/time, all marching/damping/light parameters, material decoding/color mode, display/vsync mode and power state.

Suggested future artifact layout (not generated by this research task):

```text
out/benchmarks/<run-id>/manifest.json
out/benchmarks/<run-id>/frames/*.exr
out/benchmarks/<run-id>/atlases/*.exr
out/benchmarks/<run-id>/timings.csv
out/benchmarks/<run-id>/trace-stats.json
out/benchmarks/<run-id>/comparison.json
out/benchmarks/<run-id>/review.md
```

Capture linear float outputs before display transformation and disable UI/wireframes for timed passes. Keep presentation out of offscreen comparisons. Use explicit simulation time rather than real-time input or shader-driven randomness. Preserve source asset identifiers and bake parameters.

## Initial comparison gates

- CPU well-conditioned affine round trips: relative error at most `1e-5` for float32 against double precision; reject or diagnose singular cases. Also check absolute error near zero. Scale the absolute budget to documented scene units.
- Translation fixtures: proposed hit/miss agreement at least 99.9% and 99th-percentile projected hit error at most 0.5 pixel at the recorded camera, with separate seam/silhouette regions. Review the worst 0.1% explicitly; global averages must not hide seam failures.
- Color comparison: report linear RGB MAE and maximum error, but use UV/hit/depth/normal outputs to distinguish color-pipeline differences from geometry bugs. Do not prescribe a single RGB threshold before equivalent material decoding is established.
- Animation: inspect at least 120 deterministic samples spanning a full bend cycle, including maximum compression. Require no unexplained new transient holes or repeated-teleport spikes. A human reviewer inspects seam crops and silhouette sequences.
- Optimization: proposed adoption threshold is at least 10% median improvement in its target cost over five matched runs, with no more than 5% regression in total GPU median or p95. Retain smaller improvements only with an explicit memory, clarity or portability benefit. These are project decision rules, not statistical significance claims.
- Precision packing: satisfy the same geometry gates, not just a texture PSNR number. Report sign flips, invalid determinant counts and failures by conditioning bucket.
- Port completion: actual rendering on the target device, reproducible artifacts and human review are required. Shader compilation, feature enumeration or a headless clear-color frame do not establish DASHR parity.

## Measurement procedure

1. Select a fixed fixture and parameter manifest. Warm at least 120 frames, then capture at least 300 frames; extend if thermal drift or variance persists.
2. Repeat five times, alternating A/B order. Report per-run medians and p95/p99, plus run-to-run spread. Record rejected/unreliable samples.
3. Record GPU deformation, edgefill/distortion, main shading and optional shadow contribution. Record CPU bake/import/submission separately. Capture GPU counters when supported without treating profiler-instrumented wall time as ordinary runtime.
4. Run 720p and 1080p, atlas sizes 64/128/256/512/1024 where fixtures fit. Test grazing/close-up views, shadow on/off and high deformation. Budget higher atlas sizes explicitly before allocating them.
5. Record logical allocations and observed memory use separately. Static map preprocessing and cache misses get their own timing runs; do not mix them into steady-state medians.
6. Compare equivalent formats, variants and inputs across backends. Compare Metal and wgpu on the same Mac before attributing differences to API overhead; Windows-versus-Mac numbers confound hardware, drivers and platform.
7. Publish artifact paths and explicit pass/fail results for each gate. If GPU timestamps are unavailable, use a documented synchronization method or mark GPU time unavailable; CPU submit time is not GPU execution time.

## Baselines and scope

Use a conventional coarse normal-mapped mesh for speed/quality tradeoffs, a displaced mesh at several tessellation levels for geometric quality, and the original DASHR configuration for algorithm parity. Compare similar visual quality, not only equal triangle count. Account for the expensive reference mesh preparation separately.

For general scene use, add actual-hit reverse-Z depth, two-object occlusion, shadows between assets, near clipping and camera-inside-shell tests. These are later functionality gates; the original shell-depth image is not sufficient evidence.

## Stop conditions

Stop a run on device loss, allocation failure, unresolved validation error, NaN/Inf propagation, importer ambiguity or uncontrolled time-dependent input. Save the failure manifest and do not count it as a successful performance sample. Lack of Windows captures blocks parity claims but does not prevent analytic fixtures or platform capability probes.
